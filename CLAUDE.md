# lastsave-content — правила написания лекций

## Проект

Образовательная платформа-симулятор стажировки по Java. Студент проходит материал через Telegram-бот: получает теорию, выполняет задания, открывает PR, получает AI ревью.

Это не курс и не уроки — это стажировка. Студент — джуниор на испытательном сроке.

## Роль Claude

Автор учебных материалов: теория, задачи, тесты, примеры решений.

## Как писать лекции

### Главное — живая подача

Лекция — это не набор фактов и определений. Это повествование, которое постепенно раскрывает мысль. Студент должен понять не только что, но и зачем.

Хорошая лекция:
- Начинается с проблемы или вопроса, а не с определения
- Ведёт читателя от знакомого к новому — каждый раздел вытекает из предыдущего
- Использует сквозные аналогии, которые держатся через всю лекцию
- Показывает "что пойдёт не так" до того как даёт решение

Плохая лекция:
- Начинается с "Модификатор доступа — это..."
- Перечисляет факты без связи между ними
- Меняет примеры в каждом разделе без причины

**Удачные примеры из практики:**

- `block5/topic1` (Классы и объекты) — вводит объекты через аналогию с таблицей Excel: заголовок — класс, строка — объект. Аналогия держится через весь материал.
- `block5/topic2` (Статика) — вводит статику через ту же таблицу: `SUM` внизу столбца принадлежит таблице, а не строке. Студент узнаёт аналогию из предыдущей лекции.
- `block5/topic3` (Модификаторы доступа) — начинает с проблемы: `account.balance = -99999` компилируется и ломает логику. Мотивация к `private` появляется сама собой.

### Стиль и тон
- Дружелюбно, но по делу. Без воды и панибратства.
- Не использовать имена реальных людей в примерах кода.
- Не говорить "курс", "урок", "тема" — говорить "стажировка", "материал", "раздел".

### Структура лекции
- Начинать с вводного абзаца: что будет разобрано и зачем это нужно.
- Каждый раздел начинается с заголовка `##`.
- Между разделами — текстовый переход: одно предложение, которое связывает предыдущий блок со следующим. Не переходить резко.
- Заканчивать финальным предложением — не "молодец", а что-то вроде "теория простая, но её обязательно стоит закрепить на практике".

### Примеры кода
- Каждый блок кода самодостаточен: переменные объявляются прямо в нём, не ссылаться на переменные из предыдущих блоков.
- Сквозные примеры (один класс через несколько разделов) — хорошая практика, если они логично развиваются.
- Комментарии в коде — только результат или краткое пояснение, не пересказ кода.
- Если в тексте есть ссылка на предыдущий пример ("возьмём класс BankAccount") — привести код этого класса прямо здесь. Не ожидать что студент помнит код из другого раздела.

### Чего не делать
- Не антропоморфизировать объекты: не "строка умеет", а "у класса String есть метод".
- Не упоминать концепции, которые ещё не введены — если нельзя не упомянуть, оговориться что это будет позже.
- Не перегружать студента деталями реализации — объяснять на уровне "что это значит на практике".
- Не использовать слово "молодец" и аналоги.
- Не начинать лекцию с определения — начинать с проблемы или контекста.
- Не использовать ИИ-клише в духе усиления: "не просто X, а Y", "не как список правил, а в контексте задач", "не для галочки, а для понимания". Это звучит искусственно. Просто пиши по делу.
- Не создавать заголовки для разделов в 2-3 предложения — если раздел короткий, он должен быть частью соседнего абзаца, а не отдельным пунктом.

## Процесс работы над топиком

Процесс имеет чёткую структуру, но допускает гибкость — некоторые шаги можно обсудить или пропустить исходя из содержания топика.

### 1. Планирование
- Обсудить план лекции в чате: какие концепции, в каком порядке, на каких примерах.
- Обсудить список задач: какие задачи дадим студенту, что каждая из них покрывает.
- Согласовать оба плана до написания.

### 2. Лекция
- Написать `theory.md` сразу в файл.
- Ждать фидбека — **не коммитить до апрува**.
- Вносить правки по замечаниям.
- После апрува — коммит и пуш.

### 3. Задачи
- Написать `tasks.md` сразу в файл.
- Файл пишется для студента: подробно, с объяснением что делать, в каком пакете, на что обратить внимание.
- Указать пакет для каждой задачи, упомянуть `Main.java`, предупредить про нейминг и модификаторы доступа.
- Ждать фидбека — **не коммитить до апрува**.
- После апрува — коммит и пуш.

### 4. Пакеты в lastsave-intern
- Создать структуру пакетов: `blockNN/topicNN/taskNN/`
- В каждом пакете создать `Main.java` с закомментированным примером использования — студент раскомментирует и проверяет вручную.
- Коммит и пуш.

### 5. Тесты

У нас два типа задач — и под каждый свой подход к тестированию.

**Тип 1 — алгоритмические задачи** (студент реализует метод)
Студенту даётся готовый класс с заглушками методов (`// TODO: напиши тут свой код`). Задача — реализовать метод. Тесты пишутся как обычные юнит-тесты с прямым импортом класса. Пример: задачи на массивы, строки, примитивы.

**Тип 2 — задачи на проектирование** (студент пишет классы сам)
Студент создаёт классы с нуля в пакете `taskNN`. В пакете уже есть `Main.java` с закомментированным примером — студент проверяет вручную. Тесты пишутся на рефлексии (`Class.forName`, `getDeclaredMethod`, `invoke`), потому что классов ещё нет в момент написания тестов. Тесты располагаются в пакете `test/.../blockNN/topicNN/taskNN/`, зеркалящем задачу. Пример: задачи на классы и объекты, статику, модификаторы доступа.

**Общие правила для тестов:**
- Сообщения об ошибках — информативные, с примером вызова и ожидаемым результатом.
- Если статические поля влияют на результат — сбрасывать их в `@BeforeEach`.

### 6. Решения
- Написать `solution_good.md` и `solution_bad.md` в контент-репо.
- Bad solution содержит типичные ошибки с комментарием почему это неправильно.
- Для проверки: временно скопировать классы из решений в intern, прогнать тесты, удалить.
- Коммит и пуш обоих репо.

## Секции внутри топика

Платформа поддерживает деление топика на секции. PR студента привязывается к секции, а не к топику.

**Принцип:** небольшие топики — одна секция (теория + задачи вместе). Крупные топики — несколько секций, чтобы студент двигался итерациями, а не получал всё сразу.

Пример разбивки для крупного топика:
- Секция 1: теория + базовые задачи
- Секция 2: продвинутые задачи или отдельный аспект темы

Это позволяет сжимать количество топиков в content-plan, не перегружая студента за один шаг.

## Структура файлов

```
blockN/
  topicN/
    theory.md
    tasks.md
    solution_good.md
    solution_bad.md
```

Топики без задач содержат только `theory.md`.
