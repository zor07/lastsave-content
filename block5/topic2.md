## Статические поля и методы

В прошлом разделе мы познакомились с классами и объектами. Каждый объект — это отдельный экземпляр класса со своими значениями полей. Объект `Person("Alex", 25)` хранит своё имя и возраст, объект `Person("Maria", 30)` — своё. Данные каждого объекта принадлежат только ему.

Но иногда нужно что-то другое.

Вернёмся к аналогии с таблицей Excel. Каждая строка — отдельный объект со своими данными. Но в таблице есть ещё кое-что: функции вроде `SUM` или `AVERAGE` внизу столбца. Они не принадлежат ни одной конкретной строке — они принадлежат всей таблице. Каждая строка вносит свой вклад в общий результат, но сам результат — общий.

В Java такой же механизм называется **статическим**. Статические поля и методы принадлежат классу, а не конкретному объекту.

## Статические поля

Представь что нужно считать сколько объектов `Person` было создано за время работы программы. Хранить этот счётчик в каждом объекте бессмысленно — он должен быть один на всех.

Для этого используется ключевое слово `static`:

```java
public class Person {
    String name;
    int age;
    static int count = 0;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
        count++;
    }
}
```

```java
Person first = new Person("Alex", 25);
Person second = new Person("Maria", 30);
Person third = new Person("Ivan", 22);

System.out.println(Person.count); // 3
```

Обрати внимание: к статическому полю обращаемся через имя класса — `Person.count`, а не через объект. Технически обратиться через объект (`first.count`) не будет ошибкой, но так не принято — это вводит в заблуждение, будто поле принадлежит конкретному объекту, хотя на самом деле оно общее.

Если бы `count` был обычным полем — каждый объект хранил бы своё значение, и счётчик не работал бы. Статическое поле — одно на всех.

## Статические методы

Со статическими методами та же идея — они принадлежат классу и не привязаны к конкретному объекту.

Хороший пример — утилитные методы, которые не работают с состоянием объекта, а просто выполняют вычисления над переданными данными. Именно так устроен, например, класс `Math` в стандартной библиотеке Java — у него нет полей, только статические методы:

```java
Math.max(10, 20); // 20
Math.abs(-5);     // 5
```

Создадим свой утилитный класс:

```java
public class MathUtils {

    public static int max(int a, int b) {
        return a > b ? a : b;
    }

    public static int min(int a, int b) {
        return a < b ? a : b;
    }
}
```

```java
System.out.println(MathUtils.max(10, 20)); // 20
System.out.println(MathUtils.min(10, 20)); // 10
```

Статический метод вызывается через имя класса — объект создавать не нужно.

## Ограничение статических методов

Статический метод не имеет доступа к полям объекта — потому что объекта нет. Статический метод существует на уровне класса и вызывается без создания экземпляра. Когда он выполняется — нет никакого конкретного объекта, к полям которого можно было бы обратиться. Вот почему это не скомпилируется:

```java
public class Person {
    String name;

    public static String getName() {
        return name; // ошибка: name принадлежит объекту, не классу
    }
}
```

Статический метод может работать только с тем, что принадлежит классу: со статическими полями и с тем, что передано через параметры.

Хороший пример из самой Java — метод `main`. Это точка входа в программу, именно с него начинается выполнение:

```java
public static void main(String[] args) {
    // старт программы
}
```

Он обязан быть статическим — потому что в момент запуска программы ещё не существует ни одного объекта. Некому было бы его создать. Поэтому JVM вызывает `main` напрямую через класс, без создания экземпляра.

## Когда использовать статику

Статика уместна в двух случаях:

**Утилитные методы** — когда логика не зависит от состояния объекта. `Math.max`, `Math.abs`, конвертеры, валидаторы — всё это хорошие кандидаты на статику.

**Общее состояние** — когда данные должны быть одни для всех экземпляров класса. Счётчики, константы, общие настройки.

Во всех остальных случаях лучше обычные методы и поля — так код проще понять и протестировать.
